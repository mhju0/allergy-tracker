Design audit · Allergy Tracker · 알레르기 트래커 2026-07-25 · read-only

The loudest button is the one you can't press.

This app has a real visual identity and a genuinely tested domain core. What it does not have is dynamics: every row is a hairline, every action is a full-width pill, and the one loud colour lands on whichever button happens to be first in the JSX — which, while a food trial is running, is the one action the app's own rule blocks.

PHASE 0

Inspect

Product
A private notebook for introducing a baby's first foods one at a time, so a parent can tell at a glance which foods are safe, which caused a reaction, and which is being watched right now.
Primary user
A Korean-speaking parent weaning one baby, on one iPhone, alone. No account, no second device, no partner sync.
Main user job
“Feed one new food, watch three days, record what happened, move on — and still be able to answer the paediatrician six months later.”
Main flows
Daily loop — open, tap 이상 없음, close (≈4 s, twice per 3-day window).
Start loop — 새 재료 시작하기 → pick a food → trial begins.
Close loop — window elapses → 안전으로 표시, or reaction → 반응 기록 modal.
Recall — 캘린더 / food detail / PDF export before a doctor visit.
Stack
Expo SDK 57, React Native 0.86, TypeScript strict, Expo Router (file-based, stack-only), expo-sqlite + Drizzle, i18next (ko only), expo-notifications, expo-print. npm (package-lock.json, no yarn/pnpm/bun lockfile).
UI architecture
Six route files under app/, each a single default-exported screen holding all of its own layout as inline style objects — there is no StyleSheet, no theme provider, no styled-components. Three shared components (Button, StatusChip, CheckinPill) and one token module (src/ui/tokens.ts) exporting colors, statusIcon, radii, layout. Domain logic is pure and unit-tested; the UI is a thin layer over it.
Design-system maturity
Token-based, partial. Colour is fully centralised and genuinely disciplined — zero hardcoded hex outside tokens.ts. Everything else is not: 17 distinct font sizes (10, 11, 11.5, 12, 12.5, 13, 13.5, 14, 15, 17, 18, 30, 40, 44, 52, 58 …) and 13 distinct spacing values appear as literals across the screens, with no scale to snap to. radii exports one value; there is no elevation ramp (correctly — the app has no shadows) and no motion vocabulary at all.
Risky files — do not touch
src/domain/*.ts (pure, fully unit-tested; status derivation is the product's correctness guarantee) · src/db/schema.ts + drizzle/** (schema change means a generated migration) · src/data/mutations.ts and src/data/useStartTrialFlow.ts (the one-active-trial invariant and the implicit-safe autoclose live here) · src/services/notify.ts · plugins/with-no-push-entitlement.js. Everything proposed in this report stays inside app/**, src/ui/** and src/i18n/ko.json.

Dead ends

  • DB init failure — raw error, no retry, no navigation. The app is bricked.
  • Home after 안전으로 표시 — the hero unmounts and the primary slot renders null. Nothing confirms what just happened.
  • Home between trials — the same null branch. This is the app's steady state after week one.
  • Empty search — “검색 결과가 없어요” with no offer to add the term as a custom food.
  • 사용 안내 다시 보기 — the WelcomeCard has no close and is the root route; the only exit re-commits the write.
  • Calendar event rows — name a food, offer no route to it.

Duplicate paths

  • Start a trial ×3 — picker row, food-detail button, and the cancel-and-start alert. All reach the same mutation; only the picker skips the detail page.
  • Log a reaction ×3 — Home (two branches) and food detail. Consistent, and defensible.
  • Mark safe ×3 — Home, detail, and the silent implicit-safe autoclose fired by starting the next food.

Back / close problems

  • Food detail's back label always reads 재료 even when back goes to Home.
  • The only back affordance on pushed screens is a 10 px glyph at 3.43:1.
  • Destructive alerts put 취소 on the destroying button and 닫기 on the safe one.

Orphan surfaces & buried actions

  • No orphan routes. All six are reachable from the UI — a genuinely clean graph for a stack-only app.
  • Active food's detail page — reachable only by tapping a 58 px headline with no affordance. Effectively orphaned by styling rather than by routing.
  • defaultWindowDays — a live per-install DB column, consumed in three places, with no UI anywhere. Three strings hardcode “3일” while their siblings interpolate the value; they disagree the moment that column is not 3.
  • colors.greenTint — defined and exported, zero consumers. A safe outcome leaves no mark on the calendar at all.
  • Buried > 2 taps: reaction history for a specific food (Home → 반응 count → scroll → row → detail = 4). Calendar (2, behind an unlabelled bottom row). Nothing critical is deeper than 4.
PHASE 2

Audit

Six categories, scored 1–5. The pattern: the parts built test-first are strong; the parts that were never given a scale, a state model or a vocabulary are weak. Colour is centralised and disciplined. Type, spacing, motion, feedback and terminology are not.

3A
First-run clarity
The welcome card is a real design decision and a good one — title, three numbered steps, one button, disclaimer, dismissal persisted. A parent understands the product in well under ten seconds. It loses points for what happens after: the first dashboard has an empty hero, 고위험 is asserted on a dozen foods with no definition anywhere in ko.json, and the 시작하기 write is unguarded so a failure traps the user on the card.

The ten issues worth fixing

Ranked by user impact × frequency. Severity is carried by the rule on the left: five-weight = P0, two-weight = P1, dashed = P2.

01 · P0 · HIERARCHY · risk: LOW
The only filled button on Home is the one action the app blocks
Problem
While a trial runs, 새 재료 시작하기 is the sole persimmon-filled control; the daily check-in and 반응 기록 are both outlines. Tapping it navigates to the picker, and only after the user taps a food does the one-active-trial rule fire — surfacing an alert whose only forward option cancels the trial in progress.
Why it matters
Visual dominance is a promise. This one leads a parent two taps down a path that ends in a destructive dialog, on the screen they open twice a day. It also teaches them that the app's loudest button is the wrong one.
Where
app/index.tsx:129 · src/ui/Button.tsx:18–19 · src/data/useStartTrialFlow.ts:35–62 · src/domain/status.ts:53–58
User impact
Two wasted taps per occurrence and a destructive prompt presented as the normal path; in the worst case a clean trial is cancelled to satisfy the button.
Fix
Make variant a function of trial state. Trial running → the check-in is primary, 새 재료 시작하기 becomes a nav row. Trial closed → 새 재료 시작하기 reclaims the fill. The button never moves; its weight follows the state.
02 · P0 · ACCESSIBILITY · risk: LOW
The primary button, and every piece of secondary text, fails WCAG AA
Problem
White 15/700 on #D96C3D measures 3.41:1. colors.muted at 3.43:1 carries every eyebrow, timestamp, hint, placeholder, empty state and the 안 먹어봄 status. colors.amber is 3.60:1 on paper and 3.09:1 on its own tint.
Why it matters
This app is used one-handed, at 3 a.m., by someone holding a baby, often outdoors. It is also the app you hand to a paediatrician. Four failures in a nine-colour palette is a token problem, not a screen problem — which is why it is cheap.
Where
src/ui/tokens.ts:4,13,15 · src/ui/Button.tsx:10,18,27 · 20+ call sites
User impact
Every non-headline word in the app is below the legibility floor for normal text.
Fix
Three hex values in one file. accent → #BE4F26 (4.84:1, same hue), muted → #6E675A for text (5.23:1), amber → #96631A for text (4.79:1) with #B0761F retained for marks and fills. No component changes. Resolved 2026-07-25: darken the accent and keep white labels, rather than the alternative of holding #D96C3D and switching the label to ink (which also passes, at 4.55:1, but visibly changes the control).
03 · P0 · FLOW COMPLETION · risk: MEDIUM
The window-end notification tells you to confirm, and Home doesn't offer the button
Problem
elapsed is derived from a render-time new Date(). Re-renders come only from live-query changes and a focus tick. There is no AppState listener, interval or timer anywhere in the repo. Foregrounding an already-focused Home from the 09:00 window-end notification re-runs nothing, so Home still shows the check-in pill and 3일 중 3일째 instead of 안전으로 표시.
Why it matters
This is the app's own scheduled prompt failing to deliver its own action. The parent taps a notification that says “mark it safe”, sees no way to mark it safe, and has to guess that navigating away and back will fix it.
Where
app/index.tsx:70,78 · app/food/[id].tsx:34,42 · src/services/notify.ts:34–37 · src/ui/CheckinPill.tsx:16
User impact
The close-loop — the entire reason for a 3-day window — is unreachable from the prompt designed to trigger it.
Fix
One AppState 'change' → active listener bumping the same tick the focus effect already bumps. ~6 lines in app/index.tsx; the same tick also fixes the check-in pill's midnight staleness.
04 · P0 · TRUST · risk: LOW
Starting a new food silently records the previous one as 안전
Problem
When the active window has elapsed, startTrial writes outcome:'safe' to the previous trial before inserting the new one. From the picker that is one tap: 두부 is selected, 소고기 is permanently recorded as safe, and the app pops to Home where the 안전 count silently increments. ko.json contains no string describing this.
Why it matters
This is the most consequential write in a medical-adjacent record, it is undisclosed, and the record goes into the PDF a parent hands to an allergist. The rule itself is sound and documented in the spec — the silence is the defect.
Where
src/domain/status.ts:53–58 · src/data/mutations.ts:20–25 · app/foods.tsx:172
User impact
A parent can accumulate safe verdicts they never consciously gave.
Fix
Resolved 2026-07-25: copy only, no logic change — the alternative, a confirm dialog before the autoclose, was rejected for putting a second tap on the app's most common action. Name it in the picker hint when a trial is elapsed (“소고기는 안전으로 기록돼요”), and surface it in the post-start Home state alongside the new hero (“✓ 소고기 안전으로 기록됨”).
05 · P0 · FLOW COMPLETION · risk: LOW
The app has no success state
Problem
Tap 안전으로 표시 and the hero unmounts; active is undefined, hasAnyTrial is true, and the conditional falls to : null. Home renders an eyebrow sitting directly on a button. The same empty branch is Home's steady state between trials — the most common state after week one.
Why it matters
“This food is safe” is the emotional payload of the entire product. Three days of watching resolve into a screen going blank.
Where
app/index.tsx:88,107,125–127 · src/data/mutations.ts:59–69
User impact
No closure on the core loop, and no headline on the screen the user opens most often.
Fix
Give the null branch content: the just-confirmed food in green with its completed ledger, or — between trials — “안전 9개 확인됨 · 다음 재료를 시작해 보세요”. See Direction A.
06 · P1 · FEEDBACK · risk: LOW
Nothing in the app responds to being touched
Problem
All 22 interactive elements use a static style object. No ({pressed}) => callback, no activeOpacity, no android_ripple, no TouchableOpacity — repo-wide. Selection states change after a press resolves; nothing changes during it.
Why it matters
On a screen built entirely from hairline rules at 1.25:1, press feedback is the main signal that a row is a control at all. It is also the cheapest possible way to fix the count rows, the hero name and the calendar month title all at once.
Where
src/ui/Button.tsx:13 · src/ui/CheckinPill.tsx:45 · app/index.tsx:90,133,153,166 · app/foods.tsx:94,120,156,191 · app/calendar.tsx:107,120,126,129,155 · app/food/[id].tsx:84 · app/settings.tsx:106,142,152 · app/log-reaction.tsx:80,99,125
User impact
Every tap in the app feels like it may not have registered.
Fix
One shared pressable style helper, applied at 22 call sites. opacity: pressed ? 0.55 : 1. Pure addition, no layout change.
07 · P1 · MODE ERROR · risk: MEDIUM
The same food row starts a 3-day trial or opens a detail page, depending on an invisible flag
Problem
pick=1 rewires every row from “open” to “commit”. Same title, same rows, same chips; the only tell is one 12 px muted hint at 3.43:1. PHASE 3

Direction

First, an uncomfortable observation. This UI is not generic in the usual sense — no cards, no shadows, no gradients, a real 58 px display voice, rules instead of containers. That is more opinionated than most shipping apps. But warm cream ground + heavy display type + a terracotta accent is, in 2026, the single most common look produced by design tooling. The palette is the part that reads as default; the structure is the part that could be unmistakable. So none of the three directions below changes the palette beyond the contrast repairs. They compete on structure.

The flatness is not a colour problem — it is a dynamics problem. Every row is a hairline, every action is a full-width pill, every screen is a stack of equal-weight blocks. The app's central idea — a three-day observation with a once-daily beat — is currently rendered as a 3 px grey bar. That is the opening.
DIRECTION A

관찰 일지 — The Observation Ledger

RECOMMENDED

The user should feel they are keeping a watch, not filling in a form — and should know within one second whether today's job is done.

Problem it attacks

  • Issue 01 — the dominant CTA points at a blocked action. A fixes it by making primacy a function of trial state.
  • Issue 05 — no success state. The ledger closing green is the success state.
  • Issue 03 — the ledger's “today” cell is the thing that must go stale-proof, which forces the AppState fix into the design rather than leaving it a bug ticket.
  • Phase 1 / Home — four 44 pt count rows push 캘린더 and 설정 toward the fold on a mini.

Signature element — the three-day ledger

The anonymous progress bar becomes three named, stamped cells, and the rule under each cell carries its state. Not a widget: the same object appears at three scales — live on Home, replayed on food detail, and as the tinted run of days on the calendar. One mechanic, three surfaces, nothing new to learn on the second screen.

Spacing · radius · elevation

  • 4 pt scale, strictly: 4 · 8 · 12 · 16 · 20 · 24 · 32 · 48. Screen inset 20 (from 22). layout.rowInset 10 → 12.
  • Radius: pill 999 · slot 10 (ledger cells, calendar days — replaces the current 9) · badge 4. Three values, all already approximated in the code.
  • Elevation: zero at every level. No shadows, ever. The only z-axis in this app is the iOS modal sheet. Depth comes from rule weight and type weight — this is a position, not an omission.

Motion — three behaviours, each informational

  • 120 ms · press: opacity 1 → 0.55 via Pressable's own pressed argument. No library. This is issue 06.
  • 260 ms · a ledger cell filling when a check-in lands — confirms the write happened.
  • 400 ms · the safe confirmation: hero ink → green, ledger closes. The success state, animated once.
  • Easing cubic-bezier(0,0,.2,1). Nothing else moves. react-native-reanimated is already installed; even so, the first two need only Animated from core.

Applied to the three most important screens

  • Home — eyebrow · 52 px food name · 13 px status line · the ledger · one filled action + one outline · a single 42 pt tally band (replacing four 44 pt rows, freeing ~134 pt) · three nav rows. Between trials the hero slot holds “안전 9개 확인됨” and the ledger is replaced by the last-confirmed food; it is never empty.
  • Food detail — same masthead, then the ledger replayed for the latest trial, with a reaction cutting the run at the day it happened. Actions below. History rows unchanged — they are already the best-composed list in the app.
  • Foods — untried rows lose their chip entirely (absence is untried, and it removes 45 repetitions of the same grey mark), tested foods sort first under a 기록 있음 · 10 group rule, and the count band from Home moves here as a filter row. The focusApplied / scrollToIndex / getItemLayout machinery is deleted and replaced by a filter — a net loss of code.

Cost in this codebase

  • New: src/ui/DayLedger.tsx (~70 lines), src/ui/pressable.ts (~6 lines).
  • Edited: src/ui/tokens.ts (3 hex + type/space scales), src/ui/Button.tsx (pressed state), src/ui/CheckinPill.tsx (becomes the ledger's today cell on Home), app/index.tsx (hero block, tally band, null branch), app/food/[id].tsx (ledger swap), app/foods.tsx (sort, chip, filter), src/i18n/ko.json (~12 strings).
  • Untouched: every file in src/domain/, src/db/, src/data/, src/services/, drizzle/. No schema change, no migration, no new dependency.
  • What breaks: the 47-test suite is domain-only and does not assert on layout, so nothing in it should fail. The two places to re-verify by hand are the ledger's day arithmetic against windowDays (never assume 3) and the foods list after scrollToIndex is removed.

Trade-off

The ledger is a three-cell layout, and it will look wrong at a seven-day window — which defaultWindowDays makes technically possible even though no UI sets it. It also privileges the active trial so heavily that the between-trials Home needs its own separate composition to avoid feeling hollow; that is one more state to design and maintain, not a free win. And it does comparatively little for the recall job — a parent preparing for a doctor's visit gets nothing new.

DIRECTION B

신호등 — The Traffic Light as Substrate

REJECTED

The user should feel the food list is the product — one living inventory that visibly turns from grey to green over months of weaning.

Problem it attacks

  • Issue 07 and the Foods screen generally — 45 repetitions of an identical grey chip, untried sorted above every food that has a history.
  • Phase 1 / Home — counts that navigate to a scroll position rather than a filter, with zero-count rows live and landing nowhere.

Signature element — the proportional status ribbon

A four-segment bar whose widths are the real counts, so the grey segment is 80 % of the width on day one and shrinks visibly over months. It is a legend, a filter control and the only genuinely emotional chart in the product, in four Views and no library.

Trade-off — and why it is rejected

The ribbon is near-useless at both ends of the journey: 100 % grey on day one, nearly all green at the end, informative only in the middle months. Its best ideas survive: dropping the untried chip and fixing the sort are folded into Direction A, and the ribbon itself is parked in the plan as a deferred medium-risk item.

DIRECTION C

달력이 앱이다 — Calendar-First

REJECTED

The record is the product; make the timeline the home screen and let the daily loop live inside it.

Problem it attacks

  • Issue 08 — a month grid where 33 of 34 days carry the same tint and outcomes are unmarked.
  • Phase 1 — the calendar is the app's real long-term value and sits behind an unlabelled row at the bottom of Home.

Signature element — the continuous trial bracket

Replace the month grid with a vertically scrolling week strip on which each trial is drawn as one continuous bracket spanning exactly the days it covered, food name set alongside it, reactions as notches. A Gantt chart in editorial type — genuinely unlike anything in this category, and achievable with plain Views.

Cost — and why it is rejected

High: a full rewrite of app/calendar.tsx with new layout maths, Home reduced to a shell, and a first-run experience that is markedly harder to understand than three numbered steps and a button. It optimises recall — the job a parent does perhaps four times a year, before a paediatric appointment — at the cost of the job they do twice a day. It is the right direction for a different product, and possibly the right v2 for the calendar screen alone; it is the wrong one to spend this codebase's next commits on.

Recommendation

Direction A — 관찰 일지. It is the only one of the three that touches every P0: it fixes the CTA hierarchy by making weight follow trial state, it invents the success state the app has never had, it forces the staleness bug into the design rather than leaving it a ticket, and it is where the implicit-safe autoclose finally gets disclosed. It gives the app a signature that is structural rather than chromatic — which matters, because the palette is the part that currently reads as a default, and the ledger is a mechanic no competitor in this category ships.

B was rejected because it optimises the every-three-days screen while leaving the twice-a-day screen alone, and solves none of the P0s; its two good ideas are absorbed into A and its ribbon is deferred, not discarded. C was rejected because it optimises the rarest job in the product and costs a rewrite to do it.

A is also the cheapest of the three: two new files, no schema change, no migration, no new dependency, and a net deletion in app/foods.tsx.
